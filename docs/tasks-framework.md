# Task/Agent Framework

This document describes the task/agent framework added to the TT Station agent.

## Overview

The task framework allows the agent to break a goal into steps, execute them sequentially, and report back. This enables autonomous multi-step operations that go beyond single tool calls.

## Architecture

### Data Model

- **`Task`**: A multi-step plan with a goal, ordered steps, and status tracking
- **`Step`**: A single step in a task (name, goal, tool, args, result, success, completed_at)
- **`TaskStatus`**: Queued, Running, Done, Failed, or Stopped
- **`Tasks`**: The task store (in-memory or file-backed)

### HTTP API

- `GET /tasks` - List all tasks
- `POST /tasks` - Create and start a new task
- `GET /tasks/{id}` - Get a specific task's status and steps
- `POST /tasks/{id}/stop` - Stop a running task
- `DELETE /tasks/{id}` - Delete a task

### Execution Model

1. A task is created with a goal and a list of steps
2. Each step specifies a tool to call (e.g., `box_status`, `list_models`, `remember`)
3. The task runner executes steps sequentially
4. Each step's result is recorded
5. If a step fails, the task stops and is marked as Failed
6. The user can stop a running task at any time

## Example Usage

### From the CLI (`tt-station task`)

The CLI drives the same routes. The box must be paired first
(`tt-station pair <host:port>`).

```bash
# List every task the box knows about
tt-station task --host qb2.local:8765 list

# Start a task: a goal plus ordered steps (each a read-only tool)
tt-station task --host qb2.local:8765 run "Check the box and list its models" \
  --step box_status --step list_models

# Inspect one task's steps and results
tt-station task --host qb2.local:8765 show <task-id>

# Stop a running task / delete a finished one
tt-station task --host qb2.local:8765 stop <task-id>
tt-station task --host qb2.local:8765 rm   <task-id>
```

`--step` takes `TOOL` or `NAME=TOOL`; a bare `NAME=` is a no-op "think" step.
Add `--json` (a global flag) for machine-readable output.

### From the desktop app

The **Tasks** page (sidebar) lists tasks, starts new ones (a goal plus a list
of steps), and stops or deletes them. It polls `GET /tasks` every few seconds.

### Raw HTTP

```bash
curl -X POST http://localhost:8765/tasks \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{
    "goal": "Check the box status and list available models",
    "steps": [
      { "name": "check_status", "goal": "Get the current box status", "tool": "box_status" },
      { "name": "list_models",  "goal": "List available models",     "tool": "list_models" }
    ]
  }'
```

### Checking Task Status

```bash
curl http://localhost:8765/tasks/<task-id> \
  -H "Authorization: Bearer <token>"
```

### Stopping a Task

```bash
curl -X POST http://localhost:8765/tasks/<task-id>/stop \
  -H "Authorization: Bearer <token>"
```

## Available Tools

Tasks can use any of the assistant's read-only tools:

- `box_status` - Get the box's current status
- `list_models` - List available models
- `recent_logs` - Get recent logs
- `search_documents` - Search uploaded documents
- `web_search` - Search the web
- `read_webpage` - Read a web page
- `remember` - Save a fact to memory
- `forget` - Forget a fact
- `open_app` - Open an app on the box
- `control_computer` - Control the box (volume, media, etc.)
- `open_folder` - Open a folder
- `find_files` - Find files
- `open_station` - Open a TT Station page
- `create_image` - Generate an image
- `switch_mode` - Switch the box's mode
- `run_model` - Start serving a model
- `stop_model` - Stop the current model
- `reset_chips` - Reset the chips
- `research` - Start a research job

## Example: Multi-Step Task

```json
{
  "goal": "Check the box status, list models, and remember the result",
  "steps": [
    {
      "name": "check_status",
      "goal": "Get the current box status",
      "tool": "box_status"
    },
    {
      "name": "list_models",
      "goal": "List available models",
      "tool": "list_models"
    },
    {
      "name": "remember_models",
      "goal": "Remember the available models",
      "tool": "remember",
      "args": {
        "fact": "Available models: [list from previous step]"
      }
    }
  ]
}
```

## Implementation Details

- Tasks are stored in memory by default, or can be persisted to disk
- Each task has a unique ID generated by the system
- Steps are executed sequentially in the order they appear
- If a step fails, the task stops and is marked as Failed
- Users can stop a running task at any time
- Task results are stored per-step for debugging and auditing
